# 화면 주석 Draw 렌더링 누적 성능 문제

## 증상

화면 주석 모드에서 자유곡선이나 도형을 계속 그릴수록 렌더링이 점점 무거워진다.

초반에는 마우스 움직임을 따라 선이 바로 그려지지만, 그린 내용이 많아진 뒤에는 실시간으로 따라오는 느낌이 줄고 잠깐 멈췄다가 한순간에 그려지는 듯한 현상이 생긴다.

## 현재 구조

현재 `src/draw.rs`의 `render()`는 마우스 이동, 마우스 업, 색상 변경, 펜 두께 변경 등 화면을 갱신해야 하는 시점마다 전체 화면을 다시 합성한다.

주요 흐름은 다음과 같다.

- 처음 Draw 시작 시 캡처한 전체 화면 `background`를 복사한다.
- 지금까지 확정된 모든 `commands`를 복사한다.
- `background` 위에 모든 명령을 처음부터 다시 그린다.
- 현재 그리고 있는 `draft`와 커서 프리뷰를 추가로 그린다.
- 전체 화면 크기의 버퍼를 `UpdateLayeredWindow`로 다시 올린다.

즉, 새 선 하나만 추가하는 구조가 아니라 매 프레임 “처음부터 전체 그림을 재생”하는 구조다.

## 원인

성능 저하의 직접 원인은 `render()`가 매번 다음 작업을 반복하기 때문이다.

- 전체 화면 버퍼 `state.background.clone()`
- 모든 그리기 명령 `state.commands.clone()`
- 모든 확정 명령을 `draw_command()`로 재실행
- 전체 화면 버퍼를 `UpdateLayeredWindow()`로 전송

그림이 많아질수록 `commands`와 자유곡선의 점 목록이 늘어난다. 따라서 마우스가 한 번 움직일 때 처리해야 할 작업량도 계속 증가한다.

특히 자유곡선은 `Vec<POINT>`를 여러 선분으로 나누어 `draw_segment()`를 반복 호출한다. 기존 자유곡선이 많을수록 현재 프레임에서 다시 그려야 하는 선분 수도 함께 늘어난다.

블러는 더 비싸다. `draw_blur_stroke()` 안에서 현재 버퍼를 다시 복사하고, 각 점 주변 픽셀의 평균을 계산한다. 블러 명령이 누적되면 일반 선보다 더 큰 지연을 만들 수 있다.

## 영향

이 구조는 기능 검증 단계에서는 단순하고 안전하지만, 실시간 주석 도구로는 적합하지 않다.

해상도가 높거나 멀티 모니터 환경일수록 전체 화면 버퍼 크기가 커진다. 4K 또는 다중 모니터에서는 한 번의 렌더마다 복사하고 전송하는 메모리 양도 커지므로 지연이 더 눈에 띌 수 있다.

## 개선 방향

ZoomIt 사양처럼 확정된 그림과 현재 그리고 있는 그림을 분리하는 누적 버퍼 방식으로 바꾸는 것이 좋다.

권장 구조는 다음과 같다.

- `background`: Draw 시작 시 캡처한 정지 화면
- `committed_buffer`: 확정된 그림까지 누적된 버퍼
- `preview_buffer`: `committed_buffer`를 복사한 뒤 현재 `draft`와 커서 프리뷰만 임시 합성한 버퍼
- 마우스 이동 중에는 전체 명령을 재생하지 않고 현재 `draft`만 그린다.
- 마우스 업 때 현재 `draft`를 `committed_buffer`에 확정한다.
- `Ctrl+Z`는 `committed_buffer` 스냅샷 히스토리 또는 제한된 재합성 방식으로 처리한다.

이렇게 바꾸면 마우스 이동 중 렌더 비용이 “전체 누적 그림 수”가 아니라 “현재 그리고 있는 항목 + 화면 전송 비용”에 가까워진다.

## 구현 시 주의점

- 커서 프리뷰는 실제 그림에 확정되면 안 되므로 항상 임시 합성 단계에서만 그려야 한다.
- 도형 미리보기 역시 마우스 이동 중에는 `committed_buffer`에 직접 그리지 말고 임시 버퍼에만 그려야 한다.
- `Ctrl+Z` 지원을 유지하려면 확정 전 스냅샷을 저장하거나, 명령 목록을 유지하면서 언두 시에만 재합성해야 한다.
- 블러는 원본 기준으로 적용할지, 이미 그려진 주석까지 포함해 적용할지 정책을 정해야 한다.
- 전체 화면 버퍼 복사는 남을 수 있으므로 이후에는 변경 영역만 갱신하는 방식도 검토할 수 있다.
